# app-mcp 开票约定

本项目使用 [ONEGAYI/ZCode-Plugins 的 GitHub Issues](https://github.com/ONEGAYI/ZCode-Plugins/issues)。仓库默认分支为 `master`，2026-10-10 已通过仓库元数据核实。

## 准备与发布

- 规格和票草稿先存于本项目 `docs/`，使用中文。用户确认设计、粒度与顺序后，再按其明确的发布指令创建 Issues。
- GitHub 操作优先使用已连接的 GitHub MCP；不可用时使用 `gh`。多行正文使用结构化参数，或 `--body-file` 读取已审阅的草稿。
- 本地票标识只用于准备。发布时按依赖顺序创建，并用返回的实际 Issue 编号替换引用，不猜测编号。
- GitHub 正文不能引用尚未推送的本地文档；规格可附在已授权创建的首张票内，后续票引用实际编号。研究证据使用可访问的固定版本源码链接。
- 创建 Issue 的授权不等于代码实施、推送、建 PR 或合并的授权。后续工程操作遵循仓库根规则。

## 依赖和状态

票正文写明问题、交付行为、负责模块、`Blocked by` 与可判定的验收条件。功能票围绕一个可验证行为贯穿必要层级，不按数据库、接口、UI 三层分别开票。

**宿主能力是明确的前置条件**。调研票得出“缺少入口”并关闭，不代表实现票可以开始。能力缺失时，将相应实现票保持为阻塞状态，并补充具名的上游支持依赖；未经授权不向上游仓库发票或修改研究用源码。

发布时读取现有标签；不覆盖标签、不为了套用技能自动创建一套标签。仅在已有对应标签且依赖实际满足时标记 `ready-for-agent`。标签不可用时，在正文明确状态；可选后续票不作为首版完成条件，也不默认执行。

工件区 #27 核验后，已按用户明确要求创建 `wait-for-upstreaming` 并添加到当时全部开放 Issues（#28–#31），保留既有标签。该标签不替代正文中的能力条件，也不表示已创建上游支持票。

仓库未在本项目部署 triage 技能，因此本轮不建立额外的 triage 标签体系。
